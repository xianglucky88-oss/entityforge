# 验收与发布的提交边界：协议选型与权衡

目标是证明“发布出去的字节就是验收过的字节”。下面三种协议都能做到，但在**等待成本、失败回收、验收对象绑定**上有实质区别。EntityForge 选择方案 C，并把方案 A/B 的实现钩子保留在代码里以便切换。

## 共同前提：验收对象如何绑定

无论哪种协议，绑定都不靠文件名或版本号，而靠摘要链：

1. 冻结源码清单 `source-manifest.json`（只含相对路径/字节/sha256/规范化 mode，不含绝对路径与 mtime）；
2. 每个制品记录**原始摘要与标准化摘要两组**；
3. 隔离安装后，pip 写入 PEP 610 `direct_url.json`，其 `archive_info.hashes.sha256` 直接绑定被安装的那个 wheel；
4. 报告自身的身份 `report_identity` 由“源码清单 id + 三个制品的标准化摘要 + 验收 wheel 摘要 + 解释器/工具摘要”再做一次 sha256 得到。

因此“借用另一份报告”在摘要层面不可能成立：内容不同 → 身份不同 → 提交校验拒绝。

## 方案 A：锁住整个构建

一把锁从构建开始一直持有到提交结束。

- **等待成本（最差）**：构建与隔离验收是耗时大头，全部串行。第二个发布进程必须等第一个完整跑完，即使两者内容互不相关。
- **失败回收（最简单）**：锁内只有一个进程，不存在“谁先提交”的竞争；进程崩溃只需清掉自己的工作目录。
- **验收对象绑定**：天然成立，但代价是把完全可以并行的工作也串行化了。
- 适用：构建很快、发布频率很低的场景。

## 方案 B：只锁最终提交

构建与验收并行无锁，仅在“写正式目录”这一步加锁；锁内先比较版本引用再决定胜负。

- **等待成本（低）**：昂贵阶段全部并行，锁只保护一次 rename，临界区极短。
- **失败回收（需要纪律）**：同版本不同内容时会有一个进程完成全部工作后在锁内被拒（白做的验收）；失败方必须保证**没有任何部分写入**正式目录。这要求所有写入走“同目录临时文件 + fsync + 原子 rename”，且锁内先查后写。
- **验收对象绑定**：必须在锁内重新摘要所有制品（不能信任验收时记下的字节），否则验收后被替换的 wheel 会带着旧报告混入。`releng/publish.py::verify_report` 与 `_store_object` 的 rename 前再哈希就是这道闸。
- 风险：失败方的算力浪费；若临时文件清理不到位，正式目录会堆积垃圾（需 `sweep_tmp` 回收）。

## 方案 C（选用）：按内容摘要发布，再原子切换版本引用

制品与报告进入**内容寻址对象库** `objects/<sha256>/...`，版本引用 `versions/<name>-<version>.json` 只是指向对象库的一个可原子替换的指针；flock 仅保护指针切换。

- **等待成本（最低）**：
  - 同版本同内容重跑 → 对象已存在，零重建直接复用（测试 `test_commit_then_rerun_reuses_result`）；
  - 不同内容 → 对象库 key 不同，互不覆盖，可同时落库；竞争只发生在版本指针这一步。
- **失败回收（最干净）**：
  - 对象库不可变：同 key 必同内容，否则报 collision 拒绝，杜绝“部分成功版本”；
  - 指针切换是单次 rename，磁盘失败时只有 `tmp/` 残留，正式目录里要么是旧引用要么没有，绝不会出现半成品引用（测试 `test_disk_write_failure_at_final_rename`、`test_exit_before_commit_leaves_no_partial_version`）；
  - `tmp/` 中未提升的文件可由 `sweep_tmp()` 安全删除。
- **验收对象绑定（最强）**：
  - 对象库 key 即字节摘要，验收过的 wheel 与发布出去的 wheel 共享同一个 key，物理上不可能换成“同版本不同内容”的另一份；
  - 版本引用同时记录 `report_identity` 与 `accepted_wheel_sha256`，提交时双向核对；
  - 报告身份不匹配的发布会被 `expected_identity` 拒绝（测试 `test_cannot_borrow_another_report`）。
- 代价：正式目录会保留所有历史内容对象（不可变制品库的固有空间成本，可按保留策略离线归档）。

## 竞争语义汇总

| 场景 | 行为 | 证明测试 |
|---|---|---|
| 同版本同内容重跑 | 复用已完成结果，对象库与引用不变 | `test_commit_then_rerun_reuses_result` |
| 同版本不同内容两进程 | 恰好一个提交，另一个明确失败且零部分写入 | `test_two_real_processes_same_version_different_content`（两个真实 spawn 进程 + fifo 汇合） |
| 验收后 wheel 被替换 | 提交前再哈希拒绝 | `test_staged_wheel_replaced_after_acceptance_is_rejected` |
| 暂存副本被篡改 | rename 前漂移检查拒绝 | `test_staging_copy_corruption_is_rejected_by_drift_check` |
| 提交前进程退出 | 仅 `tmp/` 残留，无版本引用 | `test_exit_before_commit_leaves_no_partial_version` |
| 磁盘写入失败 | 无部分成功，清理后可重试 | `test_disk_write_failure_at_final_rename` |

## 为什么“锁最终提交”和“内容寻址”要一起出现

单靠方案 B 的锁只能保证“同一时刻只有一个写入者”，保证不了“写入的就是验收过的字节”——验收与提交之间存在时间窗。内容寻址把时间窗问题转化为纯函数问题：发布的 key 由字节决定，而验收记录的正是同一批字节的摘要。锁只负责让版本指针的切换串行且原子，两者职责分离，缺一不可。
